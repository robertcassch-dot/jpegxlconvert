Does Your Browser Support JPEG XL?

The box below asks your browser to show three tiny JPEG XL images by itself — no plugin, no help from this site. Underneath: what the answer means, where every major browser stands in October 2026, and how to switch support on where that's possible.

The test

Your browser is handed three JPEG XL images embedded in this page — a plain one (97 bytes), one with transparency (175 bytes) and a two-frame animation (88 bytes) — and asked to draw them like any other picture. Each has its own width and height, which the test checks, so a browser can't pass by merely pretending to load them; for the transparent one it also checks that the transparent corner really comes out transparent, and for the animation it asks the browser's own decoder how many frames it reads. Browsers without that decoder interface get the animated square instead, with a note to watch whether it changes colour: we'd rather ask you to look than report a “no” we can't be sure of. If the plain one draws, your browser decodes JPEG XL natively. The test itself fetches nothing and sends nothing: the whole check happens inside your tab.

Natively is the key word. This site's viewer and converter decode JPEG XL with WebAssembly and work in every browser; the test deliberately leaves that out and checks only what your browser can do on its own, which is exactly what decides whether .jxl images on other websites will appear. The answer needs JavaScript, so with it switched off you'll see a short notice instead of the result.

What your result means

✅

Yes — it's supported

Websites can send you .jxl images and you'll see them. In Chrome 155 we could also open a .jxl straight from disk or from a link, and it displayed as an ordinary image instead of downloading. There's nothing for you to change.

❌

No — not supported

Your browser can't draw JPEG XL by itself. Well-built websites notice and send you AVIF, WebP or JPEG instead, so your browsing isn't affected. A .jxl file that someone sends you is another matter — see what to do further down.

🤔

No, but I expected yes

Almost always one of three things: an older version (Chrome before 155, Firefox before 158), Microsoft Edge, or a switch that someone turned off. The table below tells you which, and the section after it how to fix it.

Which browsers support JPEG XL in October 2026

Three engines now show JPEG XL by default: Chrome's since version 155 (6 October 2026), Firefox's since 158 (13 October 2026) and Safari's since 2023. Browsers built on those engines don't always follow them, and Microsoft Edge is the clearest case.

We ran the Chrome, Edge and Brave rows ourselves on Windows 11 on 15 October 2026, with the same method as the test — a tiny JPEG XL image embedded in the page — plus one served over HTTP and a <picture> element with a PNG fallback. Chrome and Brave drew the images and chose the JPEG XL source; Edge failed every check and fell back to the PNG, even when we forced Chromium's JPEG XL feature on from the command line. How to switch it on, where you can

Where support is built in but turned off, this takes under a minute. Where the decoder isn't in the browser at all, no setting will help — skip to the next section.

Chrome 145 to 154, and Opera

Updating is the real fix, because Chrome 155 has it on. If you can't update, paste chrome://flags/#enable-jxl-image-format into the address bar (in Opera, opera://flags/#enable-jxl-image-format), set Enable JXL image format to Enabled and press Relaunch.

Chrome 155 or later and still no

Open the same flag. If it reads Disabled, set it back to Default and relaunch — in our test, disabling it switched JPEG XL off completely. Chromium has the flag due to expire after version 158, so from then on it will vanish from the list.

Firefox 152 to 157, and ESR 153

In 152 to 157, tick Media: JPEG XL in Settings → Firefox Labs; in ESR 153, set image.jxl.enabled to true in about:config. Updating to Firefox 158 is simpler still. Our Firefox guide covers the ESR builds and the forks.

Edge, Samsung Internet, older Firefox

There's nothing to flip. Edge 155 ignored even the command-line switch in our test, Samsung Internet has no known switch (caniuse lists no flag), and Firefox before 152, ESR 140 and ESR 115 were built without the decoder. Use another browser for JPEG XL, or one of the options further down.

Then run the test again

Reload this page after relaunching. If the box now says yes, websites will get the same answer from your browser.

For web developers: how a site can tell

The Accept header. A browser that can decode JPEG XL says so in the Accept header of its image requests. In our test Chrome 155 sent image/jxl,image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8, and Brave did the same; Edge 155 left image/jxl out, and so did Chrome with the feature disabled. Firefox adds image/jxl whenever image.jxl.enabled is on. A server or CDN can use that to decide which file to send.

The <picture> element. Put the JPEG XL in a <source type="image/jxl"> with an ordinary image behind it and each browser takes what it can show. In our test Chrome and Brave downloaded only the .jxl and Edge only the PNG, so nobody wasted a byte.

Decoding, not encoding. None of these browsers can create JPEG XL. In Chrome 155, asking a canvas for image/jxl with toBlob() quietly returned a PNG, which is what the HTML standard says to do with a type the browser doesn't support. Encoding remains a job for cjxl or a converter.

Whatever the test says on your own machine, keep a fallback on a public site. Edge, older Chrome and Firefox, and every browser that simply hasn't updated yet still can't show JPEG XL, and Samsung Internet is unconfirmed. The version you test with is rarely the one all your visitors run.

FAQ

Is this test reliable?
It checks what websites rely on: whether your browser can decode a JPEG XL image natively, plus transparency and animation. A pass on the plain image means .jxl images on the web will display. It doesn't check HDR or progressive loading — Firefox, for instance, shows HDR images in standard range. Safari is the usual case for the animation row: it shows still JPEG XL images but doesn't play animated ones.
Why does Chrome say yes and Edge no, if both are Chromium?
Chromium contains the decoder, but each company decides what goes into its own build — Chromium even has a build option for leaving JPEG XL out. Microsoft removed JPEG XL from its Edge 155 release notes on 9 October 2026, and in our test Edge 155 couldn't decode it even with Chromium's feature forced on.
I enabled the flag and the test still says no
Make sure you pressed Relaunch rather than just closing the tab, because flags apply after a restart. Then check the version: the current flag only exists from Chrome 145 onwards, and in Edge it does nothing.
Does the test work on my phone?
Yes. On Android, Chrome 155 and Firefox 158 or later should pass; Samsung Internet is unconfirmed, so this test is the quickest way to find out. On iPhone and iPad the mainstream browsers all run on Apple's engine, so with iOS 17 or later they pass, just like Safari.
Does a pass mean I can save images as JPEG XL?
No. Browsers only decode the format; none of them can save to it. To create a .jxl, use a converter such as JPG to JXL, which also runs in your browser.
Does the test upload or record anything?
No. The test itself fetches nothing and sends nothing: its three images are already inside this page, the result is worked out by your own browser, and it's shown only to you.
